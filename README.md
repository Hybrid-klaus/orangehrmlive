# OrangeHRM Employee Lifecycle - QA Automation Framework

Automated UI + API test for the **Employee Lifecycle Management** scenario on the
[OrangeHRM demo site](https://opensource-demo.orangehrmlive.com/), built with
**Selenium WebDriver + Java + TestNG**, following the **Page Object Model (POM)**.

---

## Tech Stack

| Layer            | Tool / Library                          |
|-------------------|------------------------------------------|
| Language          | Java 11                                   |
| UI Automation     | Selenium WebDriver 4.21                   |
| Test Runner       | TestNG 7.10                               |
| Build Tool        | Maven                                     |
| Driver Management | WebDriverManager (Bonigarcia)             |
| API Testing       | REST Assured 5.4                          |
| Reporting         | ExtentReports (Spark HTML reporter)       |
| Data-Driven Input | Jackson (JSON) - `testdata.json`          |

## Test Scenario Covered

**Employee Lifecycle Management** (`EmployeeLifecycleTest.java`):

1. **Login** with valid credentials, verify Dashboard is visible.
2. **Add a new employee** via `PIM > Add Employee`, using data-driven input from
   `testdata.json` (first name, last name, employee ID, profile picture).
3. **Edit employee information** — search by Employee ID, update Job Title and
   Employment Status on the Job tab, verify the change is saved.
4. **Validate via API** — cross-check the employee data against an API response
   (see note below on API choice) and assert UI vs API consistency.
5. **Delete the employee** from the UI, verify it no longer appears in the
   employee list, and verify the corresponding API delete response.
6. **Logout** and confirm the session is invalidated (redirected to the login page).

Each step logs to the ExtentReports HTML report with pass/fail status, and every
assertion carries a descriptive failure message that states exactly what was
expected vs. what happened.

### Note on Employee ID
OrangeHRM auto-generates an Employee ID as soon as the "Add Employee" page
loads (it does not accept an arbitrary custom ID reliably in this demo
instance). Instead of fighting that auto-fill, `AddEmployeePage.captureAutoGeneratedEmployeeId()`
reads whatever ID the application assigns, and the test uses that captured
ID for every later step (search, edit, delete). `testdata.json`'s `employeeId`
field is kept for reference but is not force-typed into the UI.

### Note on the API validation step
OrangeHRM's public demo instance does not expose an open REST API for employee
records — it requires OAuth2 client credentials that aren't available on the
public demo. As explicitly permitted by the assessment brief ("*simulate API with
any public test API like ReqRes*"), `ApiHelper.java` uses the public **ReqRes**
API to demonstrate the request/response handling and UI-vs-API cross-check
pattern. In a real project, only the base URI and endpoint paths in `ApiHelper`
would need to change to point at the organization's actual employee API.

## Setup Instructions

### Prerequisites
- Java JDK 11 or higher installed (`java -version`)
- Maven 3.6+ installed (`mvn -version`)
- Google Chrome installed (or Firefox, if you switch `browser` in config)
- Internet access (WebDriverManager auto-downloads the matching browser driver)

### Install dependencies
```bash
mvn clean install -DskipTests
```

---

## How to Run the Test

### Run via Maven (uses `testng.xml`)
```bash
mvn clean test
```

### Run via TestNG directly (from an IDE)
Right-click `testng.xml` → **Run** (IntelliJ IDEA / Eclipse with TestNG plugin installed).

### Configuration
Edit `src/test/resources/config.properties` to change:
- `browser` → `chrome` or `firefox`
- `headless` → `true` to run without a visible browser window
- `admin.username` / `admin.password` → login credentials
- `base.url` → target application URL

### Test Data
Edit `src/test/resources/testdata.json` to change the employee details used
in the test (first name, last name, employee ID, updated job title/status).
No code changes are required to run with different data.

---

## Viewing the Report

After execution, open the generated HTML report:
```
test-output/reports/TestReport_<timestamp>.html
```
This report includes step-by-step logs, pass/fail status, and screenshots
automatically attached for any failed step.

Screenshots (on failure) are also saved separately under `/screenshots`.

## Design Notes

- **Page Object Model**: every screen is represented by a dedicated class
  exposing only user-facing actions (`loginAs`, `updateJobTitle`, etc.) — test
  code never touches locators directly, so UI changes only require updating
  one Page Object, not the tests.
- **Thread-safe driver management**: `DriverManager` uses a `ThreadLocal`,
  making the framework parallel-execution-ready if needed later.
- **Descriptive assertions**: every `Assert` call states the expected vs.
  actual condition in plain English, so a failing report is immediately
  actionable without re-running the test.
- **Data-driven design**: employee details live in `testdata.json`, not
  hardcoded in the test, so the same test can run against different data
  without touching code.
